SR-HPM · Speculative verification on RAM-resident weights for Heterogeneous PC Memory

Dense LLMs bigger than your GPU, 3.6× faster

SR-HPM is a llama.cpp patch and a launcher that make speculative decoding pay off when most of a model lives in system RAM. A 27B dense model on a 6 GB laptop GPU goes from 2.7 to ~10 tokens per second, with exactly the same output.

How it works

Decoding a model that does not fit in VRAM is bound by reading the CPU-side weights from RAM once per token. Speculative decoding verifies several drafted tokens per pass — but only helps if verifying M tokens costs about as much as one. SR-HPM makes that true on the CPU and then removes every other cost it could measure:

  1. Small-batch CPU kernels. Each weight block is decoded once and applied to all drafted tokens, with a lossless 4-bit re-encoding of IQ3 weights (one pshufb instead of grid lookups) and sign-free paths for offset-coded types.
  2. Cost-aware placement. The GPU gets the layers with the highest CPU cost per byte, plus the output head the drafter shares.
  3. Adaptive drafting. Keep 3 drafted tokens, extend to 7 while the drafter is confident.
  4. Lazy rollback for hybrid recurrent models. Two full states per pass plus exact rank-1 replay, and a split prompt path that keeps them exact at GPU speed (prefill +35 %).
  5. The idle GPU helps verify. It computes a share of the CPU layers' rows, reading them straight from RAM over PCIe.
  6. System details that add up. GPU keep-alive, 2 MB pages, op-offload fix, re-quantization tuned to what the kernels read fastest.

Install and run

Windows (Visual Studio 2022 C++ tools, CMake, Git, Python; optional CUDA 12 and LLVM):

git clone https://github.com/Javitax47/sr-hpm
cd sr-hpm
powershell -ExecutionPolicy Bypass -File scripts\install_windows.ps1
python -m srhpm.launch model.gguf --draft drafter.gguf --run

Linux:

git clone https://github.com/Javitax47/sr-hpm && cd sr-hpm
bash scripts/install_linux.sh
python3 -m srhpm.launch model.gguf --draft drafter.gguf --run

The launcher reads the model and the machine, picks the plan (all-GPU, MoE or SR-HPM), and starts an OpenAI-compatible server on 127.0.0.1:8080. Works with any dense GGUF model; the large gains need a drafter (DFlash/DFlash2 or a small model of the same family).

Use it from any app

The server SR-HPM starts is a standard llama-server with an OpenAI-compatible API. Any app, agent framework or pipeline that talks to OpenAI — LangChain, LlamaIndex, Open WebUI, Continue, n8n or your own code — uses it by changing its base URL. Chat, streaming, JSON grammars and tool calls work as usual; SR-HPM only changes how fast the tokens come out.

from openai import OpenAI
client = OpenAI(base_url="http://127.0.0.1:8080/v1", api_key="none")
r = client.chat.completions.create(model="local", messages=[{"role": "user", "content": "Hello!"}])
print(r.choices[0].message.content)

Context window, sampling and thinking

Qwen3.8-27B accepts up to 262k tokens. A q8 KV cache costs nothing measurable in quality and can live in RAM (--ctx 131072 --kv-type q8_0 --kv-ram). What costs speed is the text actually in context:

Tokens in contextTime to first tokenDecode
short chat (8k window)—9.6 tok/s
9.7k57 s5.2 tok/s (stock path: 3.4)
36k3.6 min4.1 tok/s (1.5)
100k11 min2.2 tok/s (0.5)

With a quantized cache, SR-HPM's grouped attention reads each K row once per KV head and multiplies it in int8 (identical output to the stock path) instead of re-reading the whole cache for every verified token and query head: 2.8–4.4× faster decode at 36–100k tokens. Long-context runs summarize Spanish text, where the drafter is weak. Temperature 1 instead of greedy: −9 %. Thinking mode on: 7.5 tok/s. Windows up to 32k are comfortable; larger ones suit occasional long documents.

Shorter answers, shorter waits

What you wait for is tokens ÷ speed. A one-line system prompt asking for brevity cuts the tokens far more than it costs in speed (same 10 prompts, complete answers, two rounds):

caveman ("Respond terse…")1949.8–10.2 tok/s22–23 s

Answers stayed correct (arithmetic, proofs, code with tests); preambles and closing summaries go. Thinking mode is ~14 % slower per token on top of the tokens it adds: --thinking off disables it.

What did not work

Half of the project is negative results — each idea was attacked first with the cheapest experiment that could refute it. A few:

  • Draft trees: ≤ +3 % with the real cost curve; on recurrent models a second chain duplicates the prefix.
  • 2-bit CPU layers: more quality loss (KLD 0.094) and slower — grid decoding is compute-bound.
  • Activation sparsity with a pass-shared mask: skipping 10 % of weight blocks costs 5–10× the quantization error.
  • Dropping redundant layers: two layers already more than double the KLD.
  • Reranking the drafter's 16 candidates without training: the right token is there, but telling which costs as much as verifying it.

The full list, with numbers and scripts, is in the paper and in research/.

About the name

The project began as a proposal called Speculative Residual · Hierarchical Precision Memory. Its audit refuted several pieces — a "holographic" context memory among them. What survived and became the tool is speculative verification on the CPU over weights kept in RAM, across the GPU + CPU memory of an ordinary PC, so the acronym was kept and re-read that way. The original proposals are in research/history/.
